# 记忆与回复优化记录

日期：2026-10-23。

本轮沿用现有记忆服务、关键词降级和上下文缓存，没有新增依赖或数据库字段。

| 环节 | 原问题 | 修改后的行为 |
| --- | --- | --- |
| 规则提取 | “我喜欢什么？”、假设和他人转述可能被截成用户事实 | 先判断源句，再从句首提取；保留真实自述、负面偏好和明确的“记住”请求 |
| 去重隔离 | 群聊事实可能阻止私聊保存相同事实 | 私聊、各群分别查重 |
| 召回降级 | 向量检索熔断后，具体问题直接返回空记忆 | 使用有超时限制的关键词兜底，继续应用账号、用户和群聊隔离 |
| 召回排序 | 先去重再排序可能留下较弱候选 | 先评分排序，再去掉相似内容 |
| 召回缓存 | 不同返回条数、近似字符预算、不同长问题可能复用结果 | 缓存区分实际条数、完整问题、作用域和精确预算，并保留有意义的标点 |
| 记忆提示 | 小预算被强制扩大，显式零预算被当成默认值 | 严格遵守传入预算，空间不足时不注入 |
| 多轮上下文 | 只限制单条长度，总历史可能远超预算 | 保留最近能容纳的完整轮次，维持时间顺序 |
| 回复组装 | 原始历史占满记忆空间，搜索参考未计入记忆预算 | 先计算搜索参考，为记忆预留空间，再按实际保留历史计算剩余预算 |
| 用户反馈 | 未注入提示词的记忆仍可能成为确认对象 | 只有注入了提示词的召回结果才进入本轮确认记录 |
| 索引重建 | 指定一个账号重建时也会清空共享向量集合 | 只重建指定账号，保留其他账号索引，并同步拒绝标记；全局重建保持原语义 |

这些修改改善了记忆进入回复的依据和上下文完整性；实际措辞、事实理解和语义检索效果仍取决于配置的模型。复杂混合句的规则兜底采用保守策略，可能少记其中的真实陈述。

## 2026-10-24 聊天语气与主动接话

在 `CharacterService` 组装提示词时统一补充聊天节奏要求，已有自定义模板也能生效，不改写保存的人设档案。后台风格、表情和长度参数继续覆盖默认倾向。

- 日常回复先接本轮具体的话和情绪，普通接话一两句即可，认真提问仍答完整；减少客服开场、复述和每轮问句收尾。
- 保留角色的态度和边界，亲近程度跟随已有对话。对方累、忙或不想聊时自然收尾，不用委屈或吃醋索取关注，不编造现实活动。
- 主动消息优先接最近聊到的小细节；后续接话补充或收尾，避免重新开场和重复盘问。与上条文字相同、仅标点空白表情不同的接话会拒发并留痕，不再重试。

语感示例只作参考，不作为固定话术：“今天好累，不太想说话”可以接“那先歇会儿，想说的时候再聊”；之前聊过猫团子，可以从“忽然想到团子了，有没有新照片”切入，不能凭空补出猫的近况。

没有新增依赖、数据库字段或发送频次。回归使用内存数据库、假模型和假适配器，不发送真实消息；实际语气仍需结合所配置模型观察。

## 2026-10-25 摘要细节与记忆管理

记忆通过两个时机写入：对话过程中提取独立事实；对话静默后，后台将尚未记录的内容按事件整理为历史笔记。示例配置静默时间为 600 秒、检查间隔为 300 秒，因此通常在最后一次对话后约 10–15 分钟记笔记，并不依赖“再见”等结束语。上下文超过模型预算或配置轮数时才滚动压缩，原始对话继续归档。

- 单个约 2000 字段落最多提取 8 条事实，替代原来的 3 条上限；模型提取输出预算同步增加。
- 分段笔记最多 1200 字（包含日期、用户归属），保留事件细节、约定、未完成计划及更正；工作摘要按上下文预算取四分之一，最多 1200 字。
- 超长单条及超长问答分段处理；合并笔记时逐段调用，避免再次把整段历史塞进一个请求。生成或合并失败时保留原文，重试复用已入库的分段笔记。
- 召回仍遵守每条 160 字和总提示预算，但长笔记优先选择与当前问题相关的片段，同时保留日期、用户归属。
- 管理页将记忆库选择放在概况区，常用搜索前置，高级筛选折叠并显示启用数量；对话摘要有独立标识和全文详情，手机使用紧凑统计及卡片列表。

旧摘要不会自动补全；已被截断的内容需要从仍保留的原始历史重新提取。更充分的提取和摘要可能增加模型用量；极小模型窗口仍可能拒绝摘要请求，此时原文会保留。

## 2026-10-26 检索打分与记忆 / 上下文算法升级

本轮聚焦「内置算法」本身：不新增依赖和数据库字段，配置项均有默认值，旧 `config.yaml` 无需修改即可启动。

**检索打分**
- 关键词召回改用「查询覆盖率」：按查询字符位置取并集并乘以候选集 IDF（`common.utils.keyword_coverage` / `keyword_idf`），不再按「命中个数 / 3」计分。中文 2/3/4 字重叠切片不会再把一次长词命中重复算成满命中；专有词（地名、宠物名）比「我 / 喜欢」等泛词权重更高；记忆里出现查询原句时额外加分。
- 关键词向量库（Chroma 不可用时的 `keyword` 降级）与记忆服务共用同一套打分，同时修复了写入查重误判：旧实现会把「我住在北京」与「我住在杭州」算成 1.0，从而把新住址当成重复记忆丢弃。
- `similarity()` 增加 threshold 剪枝与字符二元组分片 LRU 缓存：查重、MMR 去重只关心「是否达到阈值」时，长度上界不足或 Jaccard 已达标就跳过 SequenceMatcher；同一批内容的重复比较不再重复分片。

**记忆逻辑**
- 身份事实自动更正（`memory.supersede_enabled`）：姓名、居住地、年龄、生日变化时，新值落库后把同属性旧值标记 `rejected` 并同步向量元数据，避免新旧住址 / 姓名同时被当成可信事实召回；偏好、经历、计划不受影响，避免误删。
- 召回热度回馈（`memory.recall_reinforce*`）：本轮注入并成功回复后，后台小幅提升命中记忆的热度、命中次数和最近命中时间；按条目限频（默认 6 小时），不做每轮写放大。反复被想起的记忆自然进入热层并提高后续重排分数。
- 写入查重的相似度比较同样走 threshold 剪枝，减少后台抽取链路的 CPU 占用。

**上下文压缩 / 上下文记忆**
- 摘要失败退避（`llm.summary_retry_cooldown`）：模型超时或不可用时记录失败时间，冷却期内不再每轮重试压缩；原文与已落库笔记保持不变，冷却结束后自动恢复。
- 摘要合并分批（`llm.summary_merge_batch` / `summary_merge_chars`）：笔记较多时按字符上限分批合并，调用数从 O(笔记数) 降到 O(笔记数 / 批大小)，每次请求仍有界；少量笔记保持逐条合并，重试粒度不变。
- 摘要截断保留「开头背景 + 结尾近况」（`build_messages`）：摘要超预算时不再只留最早的历史，最近约定与状态变化能进入 Prompt。


## 2026-10-26 第二轮：查询覆盖、重复证据与并发抽取

本轮继续只改内置算法与调用编排，不新增依赖、数据库字段或前端配置页；新增配置项在 `config_example.yaml` 中均有默认值，旧 `config.yaml` 不写也会生效。

**检索：长问句不再只查句首**
- 新增 `common.utils.extract_query_keywords`：先收集查询里全部「内容二字词」（过滤功能字 / 停用词），再补充 3/4 字长短语。旧实现按 4→3→2 顺序只取前 8 个 n-gram，长问句只覆盖开头；现在「你还记得……那只猫叫什么名字吗」「我的生日是五月十号」这类句子的实体（猫叫 / 名字 / 生日 / 五月 / 十号）都能进入召回集合。
- 单字查询（「猫」「花」）不再返回空关键词；内容二字词优先保证短查询与长查询都有稳定匹配单位。
- 关键词兜底 SQL、重排、长笔记片段定位统一使用查询关键词集合；记忆标签 / 向量特征仍使用偏「少而精」的 `extract_keywords`，避免两类用途互相牵制。

**重排：与召回同一套词法口径**
- `rerank_score` 的词法项从「命中个数 / min(3, 关键词数)」改为 `keyword_coverage` + 候选集 IDF：重叠切片不重复计分，专名权重高于泛词。
- 重排权重在运行时归一化：后台把 `memory.rerank_weights` 调成任意正数比例都不会让最终分数整体漂出 0~1，阈值与 MMR 更稳定。
- 内置向量库增加候选 token 裁剪：文档频率超过 60% 的「我 / 的」不再把整个分区的倒排表并进候选；查询仍有多种 token 时优先用高区分度词圈选，最终打分仍使用完整查询向量。
- 修复 `global` 分区 `target_id` 合法为空串时退化为全库扫描的问题：global 记忆现在正常走 `(bot, global, "")` 分桶。
- 维护去重的两两比较补上 `threshold=0.92` 剪枝，判定结果不变，长库去重减少 SequenceMatcher 计算。

**记忆逻辑**
- 重复提及回馈（`memory.duplicate_reinforce*`）：用户再次说出同一条事实时不新增行，但原记忆的置信度 +0.03、热度 +0.1；按条目 24 小时限频，并在分区召回缓存中失效。这样反复确认的偏好 / 身份事实会自然升热，又不会因重复闲聊产生写放大。
- 已被用户否认（`rejected`）的完全相同记忆不再阻止**实时对话**重新建立：用户改口或重新提供事实时可以写回新条目。历史日志补处理（`memory_recovery`）保持保守语义，额外按分区精确内容跳过已否认事实，避免后台把用户明确否认过的旧内容重新复活。
- 身份事实更正（`supersede`）从「最近 60 条」改为按属性模式圈选全部历史候选（`MemoryRepo.identity_candidates`）：聊了几十轮日常后再搬家，旧住址仍会被新值作废。
- 修复 `list_for_retrieval(created_after=...)` 使用未定义变量 `created_at` 的问题（按时间窗恢复 / 过滤会直接报错）；现在使用参数 `created_after`。
- `decay_all()` 成功后递增召回缓存代际：热度衰减会改变重排分数，旧缓存不应继续提供衰减前排序。

**上下文压缩 / 上下文记忆**
- `_merge_notes` 先对分段笔记做 O(n) 精确去重，再按字符上限分批合并；重试或重叠分段产生的相同笔记不再重复喂给模型。
- 摘要截断新增句读边界：仍按「开头背景 40% + 结尾近况 60%」分配，但在目标位置附近寻找 `。！？；` / 换行，避免把约定截成半句；最终长度严格不超过预算，末尾近况优先保留。
- 长消息记忆抽取支持多段并发（`memory.extract_concurrency`，默认 2）：模型解析只做一次，各分段在信号量内并发调用；10 段长文本不再按「段数 × 超时」串行等待。单段 / 关闭 LLM 时仍走原串行与规则兜底路径。

## 2026-10-27 第三轮：内置算法与链路性能升级

本轮同样只改内置算法与调用编排，不新增依赖、数据库字段和配置项，旧 `config.yaml` 无需修改即可启动。

**进程内缓存（无 Redis 部署的默认路径）**
- `MemoryCache` 的过期清理从「每次读写都遍历整张表」改为三级惰性策略：单键就地过期（O(1)）、累计 256 次操作或 1 秒后才批量清理一次、条目数超过 20000 时按插入顺序淘汰最旧条目。旧实现里，记忆召回缓存与各种限频标记累积到几千条后，每次 `get` 都要先扫完整张表，命中率越高越慢。

**相似度 / 重排**
- `similarity()`：规范化后完全相同的文本直接返回 1.0；二元组 Jaccard 已达到阈值时直接返回。旧实现与自身注释相反——偏偏在「最容易命中」的分支上跑完整的 `SequenceMatcher`，去重扫描与 MMR 硬去重都在为它付 CPU。
- `mmr_select()`：用 `λ·score` 作为上界做分支定界，上界已低于当前最优的候选直接跳过相似度计算；选择结果与全量比较逐项一致（新增测试用升级前的实现做对照）。
- `compose_prompt()` 的长笔记片段定位：先一次性收集关键词出现位置，再用二分判断窗口是否覆盖某个出现，单次判定从 O(候选数 × 关键词数 × 窗口长度) 降到 O(关键词数 × log 出现次数)；日期与用户归属前缀仍然保留。

**上下文压缩 / 上下文记忆**
- `_compact` 增加纯内存快速判定：先用会话里已存的字符预算算「是否超预算」，未超预算时不再打开数据库。旧实现要先查 `BotAccount` / `GroupRule` / `LlmModel`、跑完 4~6 次往返，才在最后判定「无需压缩」返回。
- `_merge_notes` 统一按字符上限分批，不再按笔记条数走「逐条合并」：默认配置下最常见的 3~4 段笔记从 3~4 次串行模型调用降到 1 次，单批仍受字符数 + 条数双上限约束；只有一段笔记时直接作为摘要，省掉一次调用。
- 合并失败仍返回 `None` 保留原文（语义不变），重试时复用已落库的分段笔记，不重复调用模型。

**上下文持久化（写放大）**
- `archive` 列的语义改为「已经移出工作窗口的原文」，`get_archive()` 返回 `archive + 当前 rounds`，对外「全量原文」视图完全不变。单条消息保存不再读取并重写整段历史 JSON：旧实现每条消息的写入量是 O(历史长度)、累计 O(历史长度²)，长会话后期每条消息都要读写几十 KB 到数 MB。
- 没有归档内容时走 Core `UPDATE` 只更新快照列；判断「消息是否已离开窗口」按对象身份而不是 `(role, content, ts)`——同一秒内重复问同一句话会产生完全相同的三元组，按内容比较会漏归档。
- `get_snapshot()` 返回副本，避免把 `ttl` / `archive` 写进缓存条目、被后续保存又持久化一遍。

**记忆抽取分段**

## 2026-10-27 第四轮：查询剖析、批量写入与 token 口径

本轮仍然只改内置算法与调用编排：不新增依赖、数据库字段和配置项，旧 `config.yaml` 无需修改即可启动。

**检索：一次查询只剖析一次**
- 新增 `common.utils.KeywordQuery`：把「与候选无关」的部分（查询规范化、每个关键词在查询里的位置、被覆盖字符的 IDF 权重总和）一次算好，`score(content)` 只剩「关键词是否出现」的判定与字符权重累加。旧实现每给一个候选打分都要重新 `re.sub` 规范化查询、重新 casefold 关键词集合、再对每个关键词 `str.find` 一次——候选越多、问题越长，重复的无用功越多。
- 关键词兜底召回（`MemoryService._keyword_hits`）、候选重排（`filter_hits` / `rerank_score`）、关键词降级向量库（`KeywordVectorStore.search`）统一改为「每个候选集构造一次，循环内复用」。`keyword_coverage(...)` 保留原签名，新增可选 `profile=` 参数，旧的单次调用写法行为完全不变。
- 打分口径逐位一致：仍是「每个字符按覆盖它的最高 IDF 计一次 + 查询原句命中额外 +0.2」。新增测试内置了一份升级前的实现做对照，7 组查询 × 3 种 IDF 组合全部相等（`assertAlmostEqual(places=12)`），重排分数也验证了「传不传剖析结果相同」。

**检索：内置向量库 Top-K 改为堆**
- `BuiltinVectorStore.search` 结尾从「整表排序后切片」改为 `heapq.nlargest(limit, scored, key=分数)`：候选集可能有上万条，O(n·log k) 只保留前 k 条，结果与「稳定降序排序后取前 k」逐项一致（新增测试对 limit=1/2/3 与完整排序前缀比对）。

**记忆写入：一次抽取一批写入**
- `add_memory` 新增 `index_vector` 参数，并抽出 `index_entries()`：一次抽取的多条事实（群聊还会同步写群共享分区）合并成一次 `vector.add` 批量嵌入。旧实现每条事实一次嵌入调用——内置稀疏嵌入是纯 CPU，onnx / api provider 则每条都是一次模型请求，8 条事实因此多等 8 次网络往返，也更容易撞上服务商限流。单条写入（后台手动创建、`/remember`、上下文笔记）仍即时写索引，行为不变。
- `_find_duplicate` 新增 `recent_pool` 参数：批量写入方按分区各取一次「最近 40 条」近邻快照复用。旧实现每条事实都查一次，8 条事实＝8 次查询。本批新增的条目会追加进快照（保持最近 40 条规模），因此同批事实之间仍然互相查重——新增测试用「我喜欢喝红茶」与「我喜欢喝红茶。」验证第二条仍被判重丢弃。
- 向量写入失败仍然只记日志：数据库记忆是事实来源，索引可由重建流程恢复。

**上下文压缩：笔记复用一次查库**
- `_compact` 先把每段的日期前缀、原文指纹、转写文本算好，再用一条 `source_message_id IN (...)` 查询取回已落库的分段笔记。旧实现每段单独 `SELECT` 一次（长会话压缩常有多段），重试复用语义完全不变。

**上下文记忆：按 token 估算而不是按 UTF-8 字节**
- 新增 `common.utils.estimate_text_tokens` / `estimate_message_tokens`：汉字（含假名、谚文）按 1 token/字，其他字符按 0.3 token/字符，每条消息再加 8 token 固定开销，图片按 1024 token 保守计。
- `LLMService.input_char_budget` 从 `(window − output − 256) // 4` 改为「最坏情况全中文」的 `×0.9`，并在 `_fit_messages` 里用同一套口径替代原来的 UTF-8 字节数校验。旧口径对中文高估约 3 倍：8k 窗口只剩约 1.7k 字历史，长对话很快被摘要顶掉；现在约 6k 字，仍保留输出上限预留与 10% 安全余量（低估会触发服务商 400，因此取偏保守的一侧）。超长单条输入依旧拒绝而不是静默截断。
- 显式配置的 `llm.context_char_budget` 仍然优先，配置层行为不变。

**调用编排：超时不再白等一次**
- `chat_with_fallback` 现在先解析备用模型：若首调用是**超时**且配置了另一个备用模型，则跳过「同一模型重试一次」直接切备用模型。一次超时已经把整个 `timeout`（默认 60s）耗完，原逻辑再等一次通常只是把用户等待翻倍。没有备用模型时仍保留一次重试，避免单次网络抖动直接变成兜底话术；非超时的可重试错误（502 / 连接重置）也仍按原顺序重试。
